## 作りと判断

製品と同じfull・CPU・固定10fpsを、**別の検証Worker**で実行する。製品の設定・フレーム取得・指標計算は読み取り専用で再利用し、検証サーバのメモリ上だけで既存private helperをexportする。製品Workerの「生33点を外へ出さない」境界は変更せず、このページ内だけに33点を返す。サーバはGET専用、動画アップロード経路なし。ブラウザのネットワーク記録でもローカルGETとblobのみを確認した。

全ソースフレームを追加推論するとVIDEO modeのtracking履歴が変わるため、10fps間では直前骨格を保持する。画面／書き出し動画に「間の表示フレーム：直前の骨格を保持」と**表示時刻とサンプル時刻の両方**を出す。低信頼度を赤で示し、全pose欠損では古い骨格を描かない。ユーザーが製品の見たサンプルを確認する場合は±0.1秒で移動する。

膝・腰のほか、体幹傾斜・左右膝角度差・左右足首高さ差・足幅を候補値として併記した。膝、腰、体幹には時系列グラフと現在位置を表示する。いずれも既存 `metrics.ts` の入力／式に合わせ、良し悪しの閾値やJev入力要素は決定していない。膝の製品「最小値」がp05である点は、単一フレーム最小と分けて表示する。

製品の4集約値と推定頂点／着地時刻はページ右側にある。品質不足のとき製品結果は `metrics=null`、診断用の途中値だけを「製品非表示」として見せる。録画には原動画・骨格・サンプル時刻・フレームごとの6数値・3グラフ・検出率／ゲート・任意メモが映り込む。

## 判定不能の映像で実際に見えたこと

以下の範囲は10fpsサンプルでの欠損区間。終了時刻はexclusive（例: `[5.1, 8.7)` は5.1〜8.6秒の36サンプル）。映像の全ソースフレームを判定した結果ではない。

### kickflip_5（自己申告成功・pose全体が落ちる）

- **5.1〜8.6秒の36サンプルでpose全体なし**。9.7、9.8秒もなく、計38/101サンプル欠損。
- 録画の約6秒フレームを目視すると、空中の脚と板が大きく写る一方、頭・上半身が画面上端で切れている。骨格は描画されず、膝／腰／体幹と候補値は「—」、グラフも途切れている。
- 「脚だけは画像に見える」ことと「33点poseを取得できる」ことが別だと分かる。画角の欠けと欠損が同時に起きているが、これだけで検出失敗の原因を一つに確定はしない。

### kickflip_8（poseはあるが右下肢が低信頼度）

- poseは53/53。**右膝26と右足首28は `[0.0, 2.2)`、右つま先32は `[0.0, 1.9)`** でvisibility / presenceの閾値不足。下半身を使えるのは31/53。
- 冒頭〜約1秒の画面／録画で、両脚の投影が近く、右膝・足首・つま先の点と線が赤になることを確認した。上半身の点や腰・体幹値は残るが、下半身8点ゲートを要求する膝平均・膝差・足首差は欠損になる。
- かかと29/30も赤になるフレームがあるが、それ自体は製品の下半身8点ゲートの対象ではない。点の色だけでゲート対象部位を混同しないようREADMEに対象番号を記載した。

### ollie_4（poseはあるが左下肢が低信頼度）

- poseは57/57。**左膝25は `[0.0, 2.8)`、左足首27は `[0.0, 2.1)`、左つま先31は `[0.0, 0.5)`** で不足。下半身を使えるのは29/57。
- 約1秒の屈曲姿勢の録画フレームで左膝・足首が赤、膝角度等は「—」になる。腰相対高さと体幹傾斜は取得でき、グラフは膝だけ冒頭に長い欠損がある。
- 腰や上半身の数値が出ても、膝・足首の信頼度不足で製品全体は判定不能になることが視覚的に確認できる。

これらはモデルの出力と画面を対応させた観察であり、赤点の推定位置が正しい／誤っているというground truthの評価ではない。

## 書き出し方式と検証

`canvas.captureStream(30)` + `MediaRecorder`を採用。既存ブラウザAPIだけで数値込みのファイルを作れ、依存追加やサーバ側動画送信が不要なため。今回の6本は**WebM / VP9、1280×1050、音声なし、1×**。30fpsはcapture要求値で、固定フレーム数のオフラインencoderではない。

Chromeで6本とも最後まで再生し、デコードした映像からフレームを保存して数値・骨格・グラフを目視した。

| 出力 | 元の長さ | 録画の最後に提示されたフレーム時刻 | 再生中に観測した提示フレーム数 |
| --- | ---: | ---: | ---: |
| kickflip_10-pose.webm | 8.942s | 8.958s | 246 |
| kickflip_4-pose.webm | 11.845s | 11.812s | 266 |
| kickflip_5-pose.webm | 10.110s | 10.114s | 215 |
| kickflip_8-pose.webm | 5.305s | 5.316s | 149 |
| ollie_1-pose.webm | 6.740s | 6.749s | 171 |
| ollie_4-pose.webm | 5.706s | 5.714s | 166 |

フレーム数は再生時の`requestVideoFrameCallback`で観測した数で、ファイル内の全encoded frame数とは断定しない。実時間録画にはコマ落ち・開始終了の差があり、音声・無損失・厳密同期は対象外。タブを背景化した録画は中止する。Safari実機のMediaRecorder互換性、QuickTimeで確実に読めるMP4は未検証。

確認内容:

- Chromium 153.0.8010.12: 6本の品質結果がT11-1と一致、10fps時刻列とフレーム数、再生／一時停止、0.25×、±0.1秒、録画とdownload、解析中止、pageerrorなし、外部送信なし。
- Playwright WebKit 26.6: kickflip_10の解析、コマ送り、390pxで横overflowなし。iPhone実機の代替ではない。
- 6録画の終端までの再生、1280×1050、途中フレームと最初の映像が異なること、元動画との尺差1秒未満。3判定不能録画のフレームとビューア画面を目視。
- `pnpm lint`成功、`pnpm exec tsc --noEmit`成功、`pnpm test`は48 files / 319 tests成功。録画中止後に保存リンクを出さないこと、動画選び直しで前の集約表示を消すこと、解析中止後に再生を有効化しないことも追加で確認した。

## 製品化する場合の障害・未決事項

1. **データ境界**: 製品は集約値だけを保存し33点をWorker外へ出さない。重畳を製品へ入れるには、その境界を再設計するかWorker内OffscreenCanvas描画で保持する設計が必要。保存・再生・削除・同意も別判断になる。
2. **端末負荷と互換性**: 生33点の全サンプル保持、追加canvas、録画はメモリ・CPUを使う。今回の机上ブラウザ確認でiPhoneの発熱・background・録画成功を保証しない。
3. **時刻と骨格のずれ**: 10fps骨格の保持は最大約0.1秒の表示差を持つ。高速動作では線が体から離れて見え得る。全フレーム推論や補間は見た目を滑らかにできるが、製品が計測したデータとの区別を保つ必要がある。
4. **指標の妥当性**: 投影、スロー、画角、欠損、カメラ移動の影響がある。腰高さは跳躍高ではなく、着地時刻も接地を観測したものではない。体幹傾斜はT11-1で仮説と逆方向だったため、採点軸には未採用。
5. **動画ファイルの互換性**: WebMは今回の配布用判断材料には使えるが、端末横断の共有にはMP4 mux/encodeや音声処理、フレーム精度を別途検討する必要がある。
6. **検証サーバの構造**: private helperをメモリ上だけでexportする仕組みは、このローカルツールに限定する。製品化時は公開APIとテストを伴う共有モジュール設計へ切り出す。

T12-1のJev調査は別報告とする。ここでは候補値を視覚化しただけで、Jevへ送る要素は依頼者が動画を見てから選ぶ。
