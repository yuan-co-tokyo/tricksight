## 1. 現在値と403の理由

当時取得したCORSRulesは次表の1ルールのみ（リンク先の現在値JSONは適用後へ更新済み）。

|項目|現在値|
|---|---|
|AllowedOrigins|`http://localhost:3000`、`https://tricksight-theta.vercel.app`|
|AllowedMethods|`POST` のみ|
|AllowedHeaders|`*`|
|ExposeHeaders|`ETag`|
|MaxAgeSeconds|`3000`|

- 本番originは許可されているが、**本番originからのCORS GETは許可されていない**。presigned POSTアップロードが動いていることと整合する。通常videoの再生ができることは、CORS fetch・ピクセル取得ができることの証明にならない。
- `http://localhost:3000` のGET/Range preflight 403は **GETがないため**。originは登録済み、RangeはAllowedHeaders=`*`に含まれる。
- `http://127.0.0.1:4175` の同条件403は **originとGETの両方がないため**。localhostと127.0.0.1は別origin。Range不足ではない。
- trycloudflare originも登録されていない。先の手順ではテストごとにorigin追加/削除が必要になるため採用を勧めない。

上記は取得した設定から確定できる許可範囲。実署名URLのGET/Blob/pixel成功はまだ未検証。CORSが通っても署名失効、権限、codecの問題は別に残る。

## 2. 製品に必要な最小差分（未適用）

[適用後候補JSON](t12-2a-cors-proposed.json)は既存ルールを変更せず、下のルールを1件追加した完全な候補。現行ルールにGETを足すだけだとlocalhostへもGETが広がるため、本番だけを対象とする独立ルールにした。

```json
{
  "AllowedHeaders": ["Range"],
  "AllowedMethods": ["GET"],
  "AllowedOrigins": ["https://tricksight-theta.vercel.app"],
  "MaxAgeSeconds": 3000
}
```

製品のBlob取得は単純GET、通常再生でRangeを使う可能性をカバーする。HEADは現行実装に不要なので追加しない。ETag等の追加ExposeHeadersも不要。既存POST、origin、header、ETag、max ageはそのまま。GETを許すことはバケット公開や認証を不要にする変更ではない。署名付きアクセスの権限は引き続き必要。

追加originは本番1件だけで、localhost・preview・トンネルの許可を増やさない。このGET設定はT12-2製品機能でも必要なため、実機テスト終了ごとの削除は不要。テスト後は診断フラグをOFFにする。製品化も取りやめる場合は、追加したGETルールだけを削除する別の判断を行う。

**CORS書換えは未実施。** 承認後にも直前に現在値を再取得し、このスナップショットから他の更新がないか確認してから管理者が適用する。古い候補JSONで他の変更を上書きしない。署名済みURLの新規発行や実動画照会も今回は行っていない。

## 3. 現行案と案Xの比較

|観点|現行: scripts + Quick Tunnel|案X: アプリ内診断ルート（推奨）|
|---|---|---|
|依頼者の手数|Macで2プロセス起動、毎回originを確認してCORS追加、開発者ツールからURLコピー、端末間転送、試験後CORS削除|許可された本人が本番へログイン→履歴から診断を開く→取得→開始。初回の管理側設定後はスマホだけで実施|
|CORS変更・残る設定|トンネルoriginが変わるたび追加/削除。本番GETは別に必要|本番GETの追加1回を製品でも継続。一時origin不要|
|署名URLの露出|DOM/Networkに加え手作業コピー、クリップボード、誤共有の余地|通常履歴と同じ所有者署名のprops/DOM/Networkのみ。入力欄・クリップボード・URLクエリへ出さない。ブラウザから秘密にできるわけではない|
|本番への影響|独立サーバーなのでアプリ変更はない。実際の本番origin/配信経路は検証しない|診断コードが本番ビルドに入る。負荷、誤った認可、エラー/計測ログへの混入を防ぐ必要あり。既定OFF＋サーバー側対象者限定で遮断|
|T12-2c以降で捨てる部分|独立HTTPサーバー、署名URL入力/検査、手渡し手順、トンネル周りは製品に持ち込まない|一時診断ルート、検査用枠Worker、レポートUI/対象者限定フラグは撤去。所有者URL取得、任意開始、ライフサイクルの検証結果は製品で再利用可能|

案Xの追加実装はルート・権限ゲート・診断Clientの移植で必要。現行scriptをそのままpublic配下へ置く方式は採らない。診断の枠WorkerとT12-2bの骨格保持Workerは別物で、先回りして後者を実装しない。安全のために共有化を急がず、使い捨て部分を小さく保つ。廃棄コード量の行数は実装前には見積もらず、上記の単位で管理する。

## 4. 案Xの遮断と所有者境界（承認後の実装条件）

ルート案: `/diagnostics/pose-display/[sessionId]`。署名URLをURLパラメーターで渡さず、sessionIdから取得する。認証済み履歴に対象者だけ見える「表示診断」リンクを置き、セッションIDの手入力も不要にする。

1. サーバー専用環境変数 `POSE_DISPLAY_DIAGNOSTIC_ENABLED` が文字列 `true` の場合だけ許可。未設定/その他はOFF。NEXT_PUBLICにはしない。リンクを隠すだけでなくページ自体にも同じゲートを適用し、直URLも404にする。ルートから呼ぶ補助処理にもゲートを置く。
2. `requireCurrentUser()` で認証し、サーバー側の対象ユーザーID allowlist（空なら全員拒否）と照合する。フラグONでも一般ユーザーへは表示しない。対象ユーザーIDを文書/コミットに書かず環境設定で管理する。
3. `getPracticeSessionDetail(user.id, sessionId)` の所有者スコープで取得し、その結果だけを `createOwnedVideoPlaybackUrl(session)` へ渡す。署名helper単独は認証を行わないので、クライアントからs3Key/所有者オブジェクトを受け取って呼ばない。他人/削除済み/再生不可動画では署名しない。
4. 署名URLを含むレスポンスを静的生成・共有キャッシュ・再検証キャッシュへ入れない。診断ページのClientとWorkerはゲート通過後に遅延ロードする。未許可時は動画取得/モデル初期化なし。環境変数変更をいつ本番へ反映できるかはデプロイ構成で確認し、確実なOFFには再デプロイを含める。
5. 静的JS chunk自体はビルドに存在し、フラグでコードの秘匿を保証しない。認証情報や動画URLをchunkへ埋め込まず、認可はサーバーで強制する。OFFでも既に開いたタブや既発行15分URLが直ちに消えるとは約束しない。試験終了時は本人が診断を終了しタブを閉じる。
6. 診断の生エラー、props、動画URL、body、点列を既存アプリのログ/分析/セッションリプレイへ渡さない。固定状態名と時間・件数のみを診断JSONにする。実装時は該当ルートの観測系も確認する。動画のGETはブラウザ→S3直結、proxyは作らない。
7. 取得/計測120秒、100MiB、cancel/hidden/pagehideの破棄、通常再生へのfallbackを維持。計測保存API・AI再分析APIには接続しない。既存履歴・アップロード経路はそのまま。

必要テスト: OFFの直URL/リンク、ONでも未認証/対象者外/他人sessionの拒否、対象所有者の許可、署名失効と再読込、未許可時の署名・Worker起動なし、URLログなし、通常履歴への回帰。デスクトップでゲートを通してから限定ONにする。実機は初回MP4でS3取得・2段階play・canvas移譲を確認し、その後元MOV/反復/背景移動へ進む。Mac WebKitの成功をiPhoneの成功と置き換えない。

## 5. 承認後の依頼者向け手順案

管理側がGETルールを一度追加し、ゲート検証済み版をデプロイして本人だけ診断をONにする。依頼者はSafariでログイン→自分の動画の履歴→「表示診断」→「動画を取得」→準備後「計測と表示テストを開始」。結果JSONをコピーして共有する。同じ流れをChromeでも試す。URLコピー、トンネル起動、CORS追加/削除は依頼者の毎回操作から外す。

診断項目は現行のMP4/元MOV、同期play、video2個、非一様pixel、表示canvas、通常再生、seek/縦横/全画面、3回反復、途中取消、背景復帰、上限付近素材のメモリ/発熱を維持する。まず小さいMP4で主要3項目を確認してから残りへ進め、途中失敗を一度に切り分ける。終了後はタブを閉じ、管理側がフラグをOFFにする。実機の全完了を今回の提案で代替しない。

- 本番originのGET追加（候補JSONの1ルール追加）の承認。
- 案Xと、既定OFF＋対象者allowlist＋所有者確認という公開境界の承認。
- 承認後にT12-2aの案X実装を行い、実S3/実機を検証する。T12-2bは別途指示まで開始しない。
